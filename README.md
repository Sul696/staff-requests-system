# نظام الطلبات الإدارية

نظام ويب داخلي لموظفي الجهة لتقديم طلبات إدارية (إجازة، صيانة، دعم فني، حجز قاعة اجتماعات، مستلزمات مكتبية...) ومتابعة حالتها، مع لوحة تحكم لمسؤول النظام لمراجعة الطلبات والبتّ فيها.

مشروع تدريبي مقدّم لوزارة التعليم — مبني بتقنيات حقيقية (Backend + قاعدة بيانات + تشفير) وليس مجرد نموذج شكلي.

---

## 1. التقنيات المستخدمة (Tech Stack)

| الطبقة | التقنية | السبب |
|---|---|---|
| الخادم (Backend) | Node.js + Express.js | بسيط، منتشر، وسهل الشرح والتوثيق |
| قاعدة البيانات | SQLite عبر `better-sqlite3` | قاعدة بيانات حقيقية بملف واحد بدون الحاجة لخادم منفصل — مناسبة تمامًا لمشروع تدريبي وقابلة للترقية لاحقًا إلى MySQL/PostgreSQL |
| تشفير كلمات المرور | `bcryptjs` | تشفير أحادي الاتجاه (Hashing) بمعامل تعقيد (Salt Rounds) — لا تُخزَّن أي كلمة مرور كنص صريح أبدًا |
| المصادقة | JWT (`jsonwebtoken`) | تحقق بدون جلسات خادم (Stateless) عبر توكن موقّع تحمله كل طلبة API |
| الواجهة الأمامية | HTML + CSS + JavaScript خام (بدون إطار عمل) | يجعل الكود سهل الفهم في العرض والمناقشة، بدون تعقيد أدوات بناء |

## 3. مخطط قاعدة البيانات

**جدول `users`** (المستخدمون: موظفون ومسؤول واحد على الأقل)

| العمود | الوصف |
|---|---|
| id | المعرّف الفريد |
| name | اسم المستخدم |
| email | البريد الإلكتروني (فريد، يُستخدم لتسجيل الدخول) |
| password_hash | كلمة المرور بعد التشفير عبر bcrypt |
| department | الإدارة/القسم |
| role | `employee` أو `admin` |
| created_at | تاريخ إنشاء الحساب |

**جدول `requests`** (الطلبات المقدّمة)

| العمود | الوصف |
|---|---|
| id | المعرّف الفريد |
| user_id | رابط بصاحب الطلب (مفتاح أجنبي إلى users) |
| type | نوع الطلب |
| title / description | عنوان الطلب وتفاصيله |
| priority | عادية / عاجلة |
| status | قيد المراجعة / قيد التنفيذ / تمت الموافقة / مرفوض |
| admin_note | ملاحظة المسؤول |
| created_at / updated_at | تواريخ الإنشاء والتحديث |

المخطط الكامل موثّق في `db/schema.sql`، وينشئه الكود تلقائيًا في `db/database.js` عند أول تشغيل.

## 4. الأمان — كيف تحقق النظام من متطلبات "التشفير"

1. **تشفير كلمات المرور (Password Hashing):** لا تُخزَّن كلمة المرور أبدًا كما أدخلها المستخدم. تُمرَّر عبر `bcrypt.hashSync(password, 10)` الذي يولّد بصمة (hash) عشوائية بمعامل تعقيد 10 جولات، بحيث حتى لو تسرّبت قاعدة البيانات، لا يمكن استخراج كلمة المرور الأصلية.
2. **التحقق دون كشف المعلومات:** عند فشل تسجيل الدخول تُعاد رسالة عامة واحدة ("البريد الإلكتروني أو كلمة المرور غير صحيحة") سواء كان الخطأ في البريد أو كلمة المرور، لمنع أي طرف من معرفة أي الحسابات مسجّلة فعليًا.
3. **JWT للمصادقة:** بعد الدخول يُصدر الخادم توكن موقّع رقميًا (JWT) يحمل هوية المستخدم ودوره، صالح لمدة محددة (8 ساعات افتراضيًا). كل طلب لاحق للـ API يجب أن يرفق هذا التوكن في ترويسة `Authorization`، والخادم يتحقق من توقيعه قبل تنفيذ أي عملية.
4. **الصلاحيات القائمة على الدور (RBAC):** وسيط `requireAdmin` يمنع أي موظف عادي من الوصول إلى مسارات المسؤول (مثل تغيير حالة طلب)، حتى لو حاول استدعاء الـ API مباشرة.
5. **الحماية من حقن SQL:** كل استعلام لقاعدة البيانات يُبنى بمعاملات مُجهّزة (Prepared Statements) عبر `better-sqlite3` (مثل `db.prepare('... WHERE email = ?').get(email)`)، ولا تُدرج مدخلات المستخدم مباشرة داخل نص الاستعلام.
6. **فصل الأسرار عن الكود:** مفتاح توقيع JWT وبيانات حساب المسؤول توضع في ملف `.env` (غير مرفوع لأي نظام تحكم بالإصدارات بحسب `.gitignore`)، وليست مكتوبة داخل الكود المصدري مباشرة.

> **ملاحظة للمناقشة:** هذه إجراءات أمان قياسية على مستوى التطبيق. للنشر الفعلي داخل شبكة الوزارة يُنصح إضافيًا بربطه بتسجيل الدخول الموحّد للوزارة (SSO)، وتفعيل HTTPS، وتحديد عدد محاولات الدخول (Rate Limiting).

## 5. توثيق واجهة الـ API

جميع المسارات تحت البادئة `/api`. المسارات المحمية تتطلب ترويسة:
`Authorization: Bearer <token>`

| الطريقة | المسار | الوصف | الصلاحية |
|---|---|---|---|
| POST | `/api/auth/register` | تسجيل حساب موظف جديد | عامة |
| POST | `/api/auth/login` | تسجيل الدخول (موظف أو مسؤول) | عامة |
| GET | `/api/requests` | عرض الطلبات (طلباتي فقط للموظف، الكل للمسؤول). يدعم `?status=&type=` | مسجَّل دخول |
| GET | `/api/requests/:id` | تفاصيل طلب واحد | صاحب الطلب أو المسؤول |
| POST | `/api/requests` | تقديم طلب جديد | موظف فقط |
| PATCH | `/api/requests/:id` | تحديث الحالة أو إضافة ملاحظة | مسؤول فقط |

**مثال - تسجيل الدخول:**
```json
POST /api/auth/login
{ "email": "admin@moe.gov.sa", "password": "Admin@12345" }
```
**الرد:**
```json
{ "token": "eyJhbGciOi...", "user": { "id": 1, "name": "مسؤول النظام", "role": "admin", "department": "..." } }
```

## 6. خطوات التشغيل

```bash
# 1) تثبيت الحزم
npm install

# 2) نسخ ملف متغيرات البيئة وتعديله
cp .env.example .env
# افتح .env وغيّر JWT_SECRET وبيانات حساب المسؤول

# 3) تشغيل الخادم
npm start

# 4) افتح المتصفح على
http://localhost:3000
```

عند أول تشغيل، ينشئ النظام قاعدة البيانات تلقائيًا (`requests.db`) ويزرع حساب مسؤول واحد ببيانات ملف `.env`. سجّل الدخول بهذا الحساب لتجربة لوحة المسؤول، أو أنشئ حساب "موظف" جديد من صفحة الدخول لتجربة تقديم الطلبات.

## 7. أفكار للتطوير المستقبلي (يمكن ذكرها في التقرير كخطوات قادمة)

- ربط تسجيل الدخول بحساب الوزارة الموحّد (SSO / Active Directory)
- إشعارات بريد إلكتروني عند تغيّر حالة الطلب
- تصدير تقارير الطلبات كملف Excel أو PDF
- سجل تدقيق (Audit Log) لكل إجراء يتخذه المسؤول
- دعم إرفاق ملفات مع الطلب (مثل صورة العطل في طلبات الصيانة)
